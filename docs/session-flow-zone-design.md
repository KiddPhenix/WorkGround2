# 普通 Session「生产力迷境」体验设计

## 1. 目标

普通 Session 应让用户持续感受到四个情绪阶段：

> 接住 → 推进 → 命中 → 收好

用户每发出一个意图，都经历一次短而完整的满足循环；连续工作时，这些循环自然衔接成心流。

这里的“迷境”指人与工具高度合拍的工作状态。核心体验是快速、准确、一致，奖励始终绑定真实进展，不使用赌博、随机奖励或损失厌恶机制。

### 1.1 体验目标

- **爽**：操作立即响应，关键结果清楚落位。
- **舒服**：界面稳定、反馈克制、等待过程可理解。
- **开心**：每轮都有真实的小胜利，并明确展示用户获得了什么。
- **可控**：用户能随时追加、暂停、停止、查看和重试。
- **可信**：进度、证据、结果和失败均来自真实运行状态。

### 1.2 核心原则

1. 每次输入都立即得到反馈。
2. 每个阶段都说明当前正在做什么。
3. 每次增强反馈都对应真实成果。
4. 界面位置稳定，避免进展导致布局不断跳动。
5. 失败显式暴露，并提供安全恢复入口。
6. 用户掌握开始、继续和结束的节奏。

## 2. 单轮体验节奏

| 时间 | 用户感受 | 界面反馈 |
|---|---|---|
| 0–120ms | 指令被接住 | 发送按钮压下、消息吸附落位、轻微触感 |
| 120–800ms | 系统开始行动 | 出现“已接手”，执行轨道展开 |
| 0.8–3s | 方向明确 | 显示第一个真实动作 |
| 3s–结束 | 持续推进 | 每个有效步骤依次锁定 |
| 完成瞬间 | 得到命中感 | 结论落位、证据对齐、完成和弦 |
| 完成之后 | 轻松继续 | 出现最多三个相关下一步，不自动执行 |

### 2.1 运行态示例

```text
正在排查登录失败                          18s

[✓ 读取配置]—[✓ 定位入口]—[● 验证刷新逻辑]

发现
Token 刷新请求存在并发覆盖

当前正在
运行 8 项认证测试……
```

### 2.2 完成态示例

```text
✓ 根因已锁定

Token 刷新存在并发覆盖
3 个文件相关 · 2 条证据吻合 · 8 项测试通过

[修复并验证]  [查看证据]  [从这里分叉]
```

## 3. 核心界面：执行轨道

将普通 Session 现有的 `RunBlock` 升级为稳定的“执行轨道”。每个有意义的真实动作称为一个 **Beat**。

### 3.1 状态头

```text
正在验证登录刷新逻辑 · 18s
```

状态头始终回答：

- 当前在做什么。
- 已经运行多久。

避免使用只有“思考中”“运行中”之类缺少业务含义的文案。

### 3.2 步骤轨道

```text
[✓ 理解] [✓ 定位] [✓ 修改] [● 验证]
```

- 只展示真实发生过的步骤。
- 不生成未来占位和虚假百分比。
- 当前节点位置稳定，新节点从右侧加入。
- 用户查看历史节点时停止自动跟随。
- 点击最新节点可恢复自动跟随。

### 3.3 证据窗口

证据窗口展示当前步骤最有价值的输出：

- 相关文件和代码位置。
- 搜索命中与排除结果。
- 命令和测试摘要。
- 错误原因和恢复状态。
- 新增或更新的产物。

原始日志默认折叠，需要时再展开，避免信息噪声打断节奏。

### 3.4 控制区

运行时始终提供：

- 停止。
- 追加要求。
- 查看详情。
- 失败后重试。

这些控制保持在固定位置，不能因步骤变化而消失或移动。

### 3.5 Beat 状态

- **开始**：节点淡入并向轨道轻微吸附。
- **执行中**：低频呼吸光，周期约 1.8 秒。
- **完成**：节点向中心收紧约 2px，图标锁定。
- **发现证据**：短暂光线连接节点与证据窗口。
- **失败**：停止呼吸，保留之前已完成节点。
- **恢复**：从失败节点继续，不重播历史动画。

## 4. 反馈分级

反馈分为轻、中、强三级，避免所有事件都争抢注意力。

### 4.1 轻反馈：维持节奏

适用于读取、搜索、普通工具调用：

- 节点轻微吸附。
- 颜色由灰变亮。
- 默认无声音。
- 动画时长 120–180ms。

### 4.2 中反馈：明确进展

适用于找到相关文件、定位原因、完成修改：

- 节点锁定。
- 播放极轻的颗粒确认音。
- 证据数量短暂增强。
- 动画时长 180–260ms。

### 4.3 强反馈：成果落地

适用于根因确认、测试通过、产物生成、任务完成：

- 多个关键节点视觉对齐。
- 中心区域亮度增加约 8%。
- 播放 300–450ms 的完成和弦。
- 结果标题落下并稳定。
- 每轮最多触发一次。

禁止使用彩带、金币、全屏烟花等与工作成果无关的庆祝方式。

## 5. 声音设计

声音应由语义事件驱动，并保持确定性。相同事件使用相同声型，帮助用户逐渐形成无需查看屏幕也能理解状态的直觉。

### 5.1 声音语法

| 事件 | 声音 |
|---|---|
| 发送成功 | 低频、短促的接入音 |
| 第一个动作 | 极轻的启动音 |
| 普通步骤完成 | 单颗粒确认音 |
| 发现关键证据 | 两音上行 |
| 等待用户 | 温和悬停双音 |
| 测试全部通过 | 三音闭合 |
| 任务完成 | 完整但克制的和弦 |
| 失败 | 低音软着陆，不使用警报 |
| 重试恢复 | 一次短上行音 |

### 5.2 声音规则

- Token 输出不触发音符。
- 任意微音之间至少间隔 1.2 秒。
- 同一 `eventId` 重复投递不得重复播放。
- 失去窗口焦点时只播放“等待操作”和“完成”。
- 强完成音每轮最多播放一次。
- 提供静音、舒适、专注、活力四档。
- 音量和动态效果遵循系统辅助功能设置。

现有 `generative-music.ts` 按 Token 随机播放音符，容易产生持续噪声和不可预测节奏。应调整为阶段背景声加语义事件提示音，或仅保留为用户主动开启的独立环境音乐。

## 6. 专注隧道

进入运行状态后，界面形成轻量“专注隧道”：

- 侧边栏降低约 8%–12% 亮度。
- Session 中央区域保持正常亮度。
- 当前 `RunBlock` 轻微提高层级。
- `TaskMemoryBar` 保持可见，但降低视觉存在感。
- `ArtifactShelf` 仅在新增产物时亮起一次。
- Composer 始终可用，用户可以随时追加指令。
- 不主动隐藏系统时间、费用或 Token 消耗。
- 不强制进入全屏状态。

用户主动滚动查看历史后，系统停止自动跟随，并在右下角显示：

```text
↓ 3 条新进展
```

用户点击后才返回当前动作，避免界面抢夺控制权。

## 7. 有效小胜利

奖励必须对应用户真实获得的价值。

### 7.1 可以强化的成果

- 找到根因。
- 排除错误方向。
- 完成修改。
- 测试通过。
- 生成可打开的产物。
- 从失败中恢复。
- 记住用户偏好。
- 完成用户主动设定的目标。

### 7.2 成果文案

弱文案：

> 运行完成。

推荐文案：

> 已锁定问题：刷新 Token 时存在并发覆盖。
> 修改 3 个文件，8 项测试通过。

轻松场景可以偶尔出现一句克制的个性化反馈：

> 验证通过。这个坑已经填平了。

同类文案可以轮换，但其中的对象、数量和验证结果必须真实。

## 8. 失败与恢复

失败使用“软中断”，保留上下文和已经取得的成果。

```text
验证停在这里

✓ 已定位认证入口
✓ 已完成代码修改
! 测试环境缺少 Redis

已完成内容会保留
[补齐环境后重试] [跳过集成测试] [查看错误]
```

失败处理规则：

- 保留已完成轨道。
- 明确停止位置和具体原因。
- 解释哪些成果仍然有效。
- 提供可安全重试的入口。
- 重试从失败节点继续。
- 网络重连不清空轨道。
- 重复、乱序、迟到事件不重复动画和声音。
- 重试失败继续显式展示，不静默吞错。

## 9. 状态模型

UI 不应根据工具名称和手写字符串猜测反馈强度。Controller 或投影层应输出语义化事件，轨道、动画和声音统一从同一事件源派生。

```ts
type FlowKind =
  | "accepted"
  | "step_started"
  | "evidence_found"
  | "step_completed"
  | "waiting_user"
  | "retrying"
  | "resolved"
  | "failed";

type FlowPhase =
  | "orient"
  | "explore"
  | "change"
  | "verify"
  | "deliver";

type Evidence = {
  type: "file" | "test" | "command" | "artifact" | "finding";
  count?: number;
  summary?: string;
};

type RunEvent = {
  eventId: string;
  kind: FlowKind;
  phase: FlowPhase;
  label: string;
  detail?: string;
  status: "running" | "completed" | "failed";
  evidence?: Evidence;
  occurredAt: number;
};
```

模型要求：

- `eventId` 作为幂等键。
- 同一事件允许从 dispatch、progress 更新到 result，不新增重复节点。
- 终态不可被迟到事件回退。
- 运行状态、声音反馈和动画反馈均由 `RunEvent` 派生。
- UI 不保存独立的业务完成状态。
- 音效播放记录只负责避免重复副作用，不成为业务状态源。

## 10. 现有实现基础

### `desktop/frontend/src/components/desktop-ui/RunBlock.tsx`

已有状态头、步骤标签、详情视口、停止和重试入口，可在现有结构上升级执行轨道，无需新建平行组件体系。

### `desktop/frontend/src/store/run.ts`

已有 `RunRecord`、`RunEvent`、终态保护和按 `eventId` 幂等合并逻辑。建议扩展语义字段，同时保留当前的单一状态源和乱序保护。

### `desktop/frontend/src/lib/runEvents.ts`

现有投影层负责把 Controller wire event 转成前端运行事件，适合集中完成工具事件到 `FlowKind`、`FlowPhase` 和 `Evidence` 的语义映射。

### `desktop/frontend/src/lib/generative-music.ts`

已有音频引擎和预设，可复用信号链、音色与用户偏好。触发逻辑应从 Token 驱动调整为语义事件驱动。

## 11. 明确禁止的机制

- 随机奖励和随机视听反馈。
- “差一点成功”的近失提示。
- 与真实状态无关的假进度。
- 连续登录奖励或中断惩罚。
- 隐藏运行时间、费用或 Token 消耗。
- 将失败包装成成功音效。
- 完成后自动开始下一轮。
- 为增加使用时长而制造无意义步骤。
- 根据用户疲劳或挫败状态诱导继续使用。

## 12. 实施顺序

### 第一阶段：建立核心节奏

1. 统一语义化 `RunEvent`。
2. 将 `RunBlock` 改造成稳定的执行轨道。
3. 发送后立即显示“已接手”。
4. 结论、证据和下一步在原位置收束。
5. 将 Token 音乐调整为事件声景。
6. 失败时保留进度并提供原位重试。

### 第二阶段：增强沉浸体验

1. 加入专注隧道。
2. 加入 Artifact 新增反馈。
3. 支持追加指令进入下一拍。
4. 提供舒适、专注、活力反馈强度。
5. 针对排障、编码、研究和内容生成调整节奏，但保持同一套语义模型。

## 13. 验收标准

### 功能验收

- 用户发送后 120ms 内获得本地视觉响应。
- 正常情况下 3 秒内展示第一个真实动作或明确等待原因。
- 每个轨道节点均能追溯到真实事件。
- 重复事件不产生重复节点、声音或动画。
- 用户滚动后不被自动拉回最新位置。
- 失败后可以从明确节点重试，已完成成果不会消失。
- 完成后最多显示三个与结果相关的下一步。

### 体验验收

> 用户闭着眼听声音、睁眼看轨道，都能感到系统正在稳定推进；完成后清楚知道得到了什么，并自然想做下一件有价值的事。

北极星指标应关注“验证完成的有效工作数量”，不以使用时长作为优化目标。辅助观察首次有效动作时间、任务完成率、失败恢复率、下一步采用率、音效关闭率和用户主动中断率。
